# Marketplace Notification Service

Transactional email delivery for the Marketplace platform: verification, password-reset, and password-changed emails, plus a generic templated/direct email API. Delivery runs asynchronously through Celery, with status tracking, retries, and delivery-attempt history stored per notification.

## Included endpoints

```text
GET  /
GET  /health
GET  /ready

POST /api/v1/notifications/email/verification
POST /api/v1/notifications/email/password-reset
POST /api/v1/notifications/email/password-changed
POST /api/v1/notifications/email/template
POST /api/v1/notifications/email/direct

GET  /api/v1/notifications
GET  /api/v1/notifications/operations/summary
GET  /api/v1/notifications/operations/ready
GET  /api/v1/notifications/{notification_id}
POST /api/v1/notifications/{notification_id}/retry
POST /api/v1/notifications/{notification_id}/cancel
POST /api/v1/notifications/{notification_id}/send-now
```

All `/api/v1/notifications/*` endpoints require an `X-Internal-API-Key` header — these are internal service-to-service endpoints, not public API. `/`, `/health`, and `/ready` are unauthenticated.

## Run with Docker

```powershell
Copy-Item .env.example .env
docker compose up --build
```

This starts four containers for the service: the API (`marketplace-notification-service`), the Celery worker (`marketplace-notification-worker`), a dedicated Postgres database, and a dedicated Redis instance (used as both the cache and the Celery broker/backend). The API container runs `alembic upgrade head` before starting; the worker does not touch migrations.

- Swagger: http://localhost:8002/docs
- Health: http://localhost:8002/health
- Readiness (checks DB + email provider): http://localhost:8002/ready

Swagger UI has an **Authorize** button (top right) for `X-Internal-API-Key` — set it once and it applies to every protected endpoint's "Try it out" call.

When running inside Docker, connect to service DNS names, not `localhost`:

```env
DATABASE_URL=postgresql+asyncpg://marketplace:marketplace@marketplace-notification-db:5432/marketplace_notifications
REDIS_URL=redis://marketplace-notification-redis:6379/1
CELERY_BROKER_URL=redis://marketplace-notification-redis:6379/1
CELERY_RESULT_BACKEND=redis://marketplace-notification-redis:6379/2
```

## Run locally

```powershell
uv sync
Copy-Item .env.example .env
```

For local execution outside Docker, set `.env` for how dependencies are running:

If Postgres/Redis run on your host directly:

```env
DATABASE_URL=postgresql+asyncpg://marketplace:marketplace@localhost:5432/marketplace_notifications
REDIS_URL=redis://localhost:6379/1
```

If you reuse Postgres/Redis from this compose stack (published ports):

```env
DATABASE_URL=postgresql+asyncpg://marketplace:marketplace@localhost:5434/marketplace_notifications
REDIS_URL=redis://localhost:6381/1
CELERY_BROKER_URL=redis://localhost:6381/1
CELERY_RESULT_BACKEND=redis://localhost:6381/2
```

Then run the API and the worker in separate terminals:

```powershell
uv run alembic upgrade head
uv run uvicorn app.main:app --reload --port 8002
```

```powershell
uv run celery -A app.celery_app worker --loglevel=info -Q notifications,notification-retries
```

## Email providers

`EMAIL_PROVIDER` selects the delivery backend:

- `console` — logs the rendered email instead of sending it; the default for local development, requires no credentials.
- `smtp` — sends through the SMTP server configured by `SMTP_HOST`/`SMTP_PORT`/`SMTP_USERNAME`/`SMTP_PASSWORD`/`SMTP_USE_TLS`/`SMTP_USE_SSL`.

Additional provider clients (not wired into `EMAIL_PROVIDER` selection yet) are available as optional extras: `smtp` (aiosmtplib), `aws`, `sendgrid`, `mailgun`, `azure`, `google`. Install with, e.g.:

```powershell
uv sync --extra sendgrid
```

## Run tests

```powershell
uv run pytest -q
```

The suite uses an isolated in-memory SQLite database and covers:

- Notification creation (direct, templated, verification, password-reset, password-changed)
- Delivery, retryable failures, permanent failures, and internal-defect handling
- Retry and cancel state transitions, including `reset_retry_count`
- Worker-crash duplicate-send protection
- Internal API key authentication
- Celery retry/backoff configuration
- Jinja2 template rendering

## Token handling

This service does not mint verification or password-reset tokens. The caller (the Auth Service) generates the token/URL and passes it in the request body to `POST /email/verification` or `POST /email/password-reset`; this service only renders the template and delivers it.
